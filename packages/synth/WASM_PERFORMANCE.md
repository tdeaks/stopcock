# WASM Performance Findings

## Implemented in this pass

- Offline `render()` now uses a compact binary graph handoff when the embedded WASM exports `stopcock_synth_render_binary`.
- Public offline `render()` is now WASM-only. The JS renderer remains available only as the explicit `renderReference` test/benchmark oracle, not as a silent production fallback.
- The production `render/offline` module now contains only the WASM entrypoint. The JS DSP oracle lives in `render/reference`, so `@stopcock/signal` biquad/convolution helpers and TypeScript oscillator kernels are not part of the public render module.
- The old JSON ABI remains in Rust and TypeScript for compatibility helpers, but it is no longer the preferred path.
- Binary requests encode graph structure, node fields, modulation edges, inputs, buffers, IRs, FM operators, and wavetable banks as little-endian bytes.
- The fallback JSON request serializer now lives in `render/wasm-json`, and render input validation now lives in `render/render-inputs`. The main `render/wasm.ts` bridge is left to orchestrate binary/runtime requests, WASM memory I/O, triggered rendering, and test/benchmark hooks.
- The TypeScript WASM render bridge is split by render path: `wasm-single` owns one-shot offline renders, `wasm-runtime-render` owns block runtime rendering, `wasm-triggered` owns triggered runtime/legacy comparison flows, and `wasm-output` owns heap copy/mix helpers. The public `wasm.ts` module is now only the availability/test/bench orchestration surface.
- The extracted WASM heap output helpers now have direct unit coverage for mono/stereo voice accumulation, stereo-to-mono heap copying, and mono heap blocks being added into stereo trigger outputs, so the JavaScript side of the WASM boundary is guarded outside broad render parity tests.
- The public TypeScript node-builder facade now mirrors the Rust runtime family split: source, routing, filter, envelope, effect, instrument, modulation, and shared common helpers live under `src/nodes/`, while `nodes.ts` remains a small compatibility export surface. This keeps the browser/docs API stable while making future Rust-native nodes easier to thread through one family at a time.
- Public TypeScript param metadata is split the same way: `params/tables` owns stable param-name tables plus `PARAMS_BY_KIND`, while `params/default-values` owns the node-specific default lookup used by worklet parameter initialization. `params.ts` stays as the compatibility export surface for existing callers.
- Binary graph payloads are cached per frozen root node, so repeated public `render()` calls reuse the compiled node walk and static node serialization while still writing per-call duration, sample-rate, trigger, and input data.
- The binary offline WASM entrypoint now renders through the typed runtime core instead of the older full-buffer graph engine, so public `render()` shares the same compiled node dispatch used by live playback.
- The JSON compatibility WASM export now also renders through the typed runtime core and writes directly into caller-owned output buffers, keeping the old ABI while avoiding the legacy full-buffer engine and intermediate `Rendered` allocation on that path.
- The binary offline WASM FFI now renders directly into the caller-provided output buffers instead of first allocating a Rust `Rendered` output and then copying that into WASM memory.
- Triggered offline WASM rendering now creates one typed runtime for the shared graph, then calls `stopcock_synth_runtime_reset_event` for each note. This avoids decoding the graph and rebuilding DSP state for every trigger while preserving fresh-voice state.
- Triggered offline WASM rendering now trims each note to a proven finite active window when the root graph is a simple gated voice or exact wrapper around one. Zero-feedback delay, classic chorus, micro-pitch, and no-feedback/fully-open-tone multi-tap delay tails are bounded by their exact maximum delay windows; reverb/filter/feedback/tone-smoothed tails still render conservatively until they have explicit measured tail bounds.
- The finite-trigger-tail analysis now lives in a reusable `render/wasm-tail` module instead of being embedded in the main TypeScript WASM bridge. The public test hook still exercises the same exact frame-bound logic used by triggered runtime rendering.
- Embedded WASM loading, export typing, base64 decoding, and direct-runtime capability detection now live in `render/wasm-instance`, leaving the main bridge focused on render orchestration and binary graph serialization.
- Binary graph writing now has a reusable `render/wasm-binary-writer` module for the growable little-endian writer and stable numeric node/param code maps. The main bridge still owns high-level node serialization, but no longer carries the low-level writer and code table details inline.
- High-level binary graph serialization now lives in `render/wasm-binary`, including graph caching and binary render/runtime request construction. Typed node-field encoding and shared Space Echo head mapping now live in `render/wasm-binary-node`, with focused tests for packed live-input remapping and head-mode booleans. The main WASM bridge now validates render inputs once and reuses the cached graph bytes for the binary render request.
- The Rust binary decoder is split into a small request envelope plus reusable `binary::reader`, `binary::codes`, and `binary::fields` modules. Reader and stable-code-map unit tests now guard the byte-level ABI that TypeScript writes and Rust decodes.
- The stateful Rust runtime keeps its block-processing engine in `runtime.rs` and its reset/block/parity coverage in `runtime/tests.rs`, so the hot runtime flow is short without losing private state coverage.
- Runtime parameter id assignment now lives in `runtime_params::ids`, including the stable scalar, FM operator, and FM matrix id tests. `runtime_params.rs` is left to own slot lookup, sparse modulation spans, and per-sample value resolution.
- Multi-tap delay binary serialization now writes tap ratios, gains, and pans through a mapped writer helper instead of allocating three temporary arrays before copying them into the request.
- The Rust FM renderer no longer allocates formatted parameter names or default operators in the per-sample inner loop.
- A persistent Rust block runtime now exists behind `stopcock_synth_runtime_new`, `stopcock_synth_runtime_process`, and `stopcock_synth_runtime_free`.
- The runtime owns reusable per-node buffers and state for oscillators, FM, noise, buffer playback, filters, delay lines, reverb history, chorus/ensemble chorus, space echo, compressor envelopes, bitcrush/degrade holds, and envelopes.
- TypeScript now detects the runtime exports and has a test bridge that renders a graph in 128-frame blocks through the stateful ABI.
- The AudioWorklet compiler now emits a WASM bridge when the embedded blob exists. The generated processor copies WebAudio inputs and `AudioParam` blocks into WASM memory, calls `stopcock_synth_runtime_process`, and copies the WASM output back.
- `play()` now routes every synth graph through the worklet path, so simple oscillator/gain/filter graphs no longer stay on the native WebAudio builder while complex graphs use WASM.
- The old native WebAudio builder has been removed from the live playback implementation, leaving the WASM AudioWorklet bridge as the only live render path.

## DSP source notes

- Biquad filters follow the [RBJ/W3C Audio EQ Cookbook](https://www.w3.org/TR/audio-eq-cookbook/) coefficient family.
- Fractional/modulated delay reads use linear interpolation, matching the practical delay-line guidance in Julius O. Smith's [Physical Audio Signal Processing material](https://www.dsprelated.com/freebooks/pasp/Delay_Line_Signal_Interpolation.html).
- The micro-pitch primitive follows the common delay-based pitch-shifter structure: two time-varying delay reads with crossfaded gains to avoid read-head discontinuities, matching the algorithm notes in MathWorks' [delay-based pitch shifter example](https://www.mathworks.com/help/audio/ug/delay-based-pitch-shifter.html) and Miller Puckette's [pitch shifting discussion](https://msp.ucsd.edu/techniques/latest/book-html/node115.html).
- The multi-tap delay primitive follows tapped-delay-line early-reflection practice: separate delayed taps are scaled and spatialized, with fractional reads when delay times are non-integer. Source notes: Julius O. Smith's [delay-line overview](https://ccrma.stanford.edu/~jos/pasp/Delay_Lines.html), his [delay-line interpolation notes](https://ccrma.stanford.edu/~jos/pasp/Delay_Line_Interpolation.html), and Gary Scavone's [early reflections notes](https://caml.music.mcgill.ca/~gary/307/week6/node9.html).
- The saturator primitive follows common waveshaping practice with a smooth tanh transfer curve, optional asymmetry for even-order content, and tone/DC cleanup. Source notes: RingBuffer's [waveshaping overview](https://ringbuffer.org/sound_synthesis_introduction/Distortion/waveshaping/), Elementary Audio's [distortion and saturation tutorial](https://www.elementary.audio/docs/tutorials/distortion-saturation-wave-shaping), and DAFx-16 aliasing-reduction notes for future antialiasing work (https://dafx.de/paper-archive/2016/dafxpapers/20-DAFx-16_paper_41-PN.pdf).
- The wavefolder primitive follows the periodic/foldback waveshaping family: pre-gain pushes a signal past a fold threshold, the transfer curve reflects it back instead of clipping, and the nonlinear core is oversampled/filtered to reduce audible aliasing. Source notes: RingBuffer's [wavefolding overview](https://ringbuffer.org/sound_synthesis_introduction/Distortion/wavefolding/), Miller Puckette's [waveshaping discussion](https://msp.ucsd.edu/techniques/latest/book-html/node78.html), and MusicDSP's waveshaper note on oversampling nonlinear transfer functions (https://www.musicdsp.org/en/latest/Effects/114-waveshaper-simple-description.html).
- The degrade primitive follows bitcrusher practice by combining resolution reduction with sample-rate division/sample hold, with mix/tone controls to keep the result musical. Source notes: Apple's Logic Bitcrusher parameter docs (https://support.apple.com/guide/logicpro-ipad/bitcrusher-lpip67e9decb/ipados), Audio Precision's TPDF dither overview (https://www.ap.com/news/dither), and the existing RBJ/W3C filter guidance for tone filtering.
- The tilt EQ primitive uses a complementary one-pole low/high split with inverse half-gains around the pivot frequency, giving a cheap first-order tone-shaping control rather than a resonant EQ band. The one-pole section reuses the same stable filter building block family referenced by the RBJ/W3C Audio EQ Cookbook (https://www.w3.org/TR/audio-eq-cookbook/).
- The state-variable filter primitive follows the trapezoidal integrated/zero-delay-feedback SVF family used for audio-rate-friendly virtual analog filters: simultaneous low, band, high, and notch outputs from one topology-preserving state update. Source notes: Andrew Simper's Cytomic SVF papers (https://cytomic.com/files/dsp/SvfLinearTrapezoidalSin.pdf and https://www.cytomic.com/files/dsp/SvfLinearTrapOptimised.pdf) and Vadim Zavalishin's VA filter design notes (https://noisehack.com/research/VAFilterDesign_1.0.3.pdf).
- The stereo-spread primitive follows the Haas/delay widening family: one side stays direct while the opposite side is delayed by a short, finite offset, then blended with mid/side widening. Source notes: Physical Audio Signal Processing delay-line guidance (https://www.dsprelated.com/freebooks/pasp/Delay_Line_Signal_Interpolation.html) and Sound On Sound's Haas-effect overview for short-delay stereo widening context (https://www.soundonsound.com/techniques/haas-effect).
- The frequency-shifter primitive follows the audio frequency-shifter/single-sideband family: a Hilbert-derived quadrature signal is mixed with a sine/cosine oscillator so partials move by a fixed Hz offset rather than a pitch ratio. Source notes: MathWorks' single-sideband/Hilbert-transform example (https://www.mathworks.com/help/signal/examples/single-sideband-modulation-via-the-hilbert-transform.html) and Scott Wardle's DAFx-98 Hilbert-transformer frequency-shifter paper (https://www.dafx.de/paper-archive/1998/WAR19.PS.pdf).
- The rotary-speaker primitive follows the classic split-rotor cabinet model: a crossover feeds a bass rotor and treble horn, separate motor speeds/rotor geometry create Doppler/vibrato and amplitude/tremolo components, and stereo mic distance changes perceived width. Source notes: Hammond/Leslie 2101 manual discussion of crossover, high/low rotors, Doppler pitch variation, and loudness variation (https://hammondorganco.com/wp-content/uploads/2011/03/Leslie2101manual.pdf), Reason Studios' Rotor manual for horn/drum split, crossover, Doppler length, speed switching, and mic distance controls (https://docs.reasonstudios.com/plusre/rotor-rotary-speaker), and Harmony Central's rotary-cabinet overview for the common 800 Hz crossover, horn/drum RPM ranges, and AM/FM character split (https://www.harmonycentral.com/articles/uncategorized/rotary-speaker-cabinet-miking-r94/).
- The ensemble chorus primitive follows the classic mono-to-stereo chorus topology: modulated hard-panned delay lines, opposite channel LFO phase, BBD/tone filtering, warm noise, and equal-power dry/wet. Source notes: Roland's Juno-60 overview (https://articles.roland.com/juno-60-the-whole-story/) and Arturia's Chorus Jun-6 manual notes on signal flow, 0.400 Hz default rate, 4.44 ms default depth, 180 degree default phase, and equal-power mix (https://manualsnet.com/arturia/chorus-jun-6).
- The tape delay primitive follows tape-echo control behavior: delay time, feedback/repeats, high-cut/tone loss, modulation depth, wow/flutter, input clipping, and tape-age fidelity loss. Source notes: Roland's Space Echo parameter guide (https://static.roland.com/manuals/gx-100_parameter/eng/25630236.html), Universal Audio's RE-201 manual notes on input clipping, tone, head timing, self-oscillation, and tape age (https://help.uaudio.com/hc/en-us/articles/33538271334164-Roland-RE-201-Space-Echo-Manual), and Physical Audio Signal Processing delay-line interpolation guidance (https://www.dsprelated.com/freebooks/pasp/Delay_Line_Interpolation_Summary.html).
- The plate reverb primitive follows the Dattorro-style plate topology: predelay, cascaded input diffusers, tank diffusers, cross-feedback decay, high-frequency damping, and modulated delay taps for tail movement. Source notes: Jon Dattorro's Effect Design Part 1 paper (https://freeverb3-vst.sourceforge.io/doc/EffectDesignPart1.pdf), Csound's Freeverb notes on parallel comb/allpass stereo reverb structure (https://csound.com/docs/manual/freeverb.html), and Physical Audio Signal Processing Freeverb notes on lowpass-feedback comb damping (https://www.dsprelated.com/freebooks/pasp/Freeverb.html).
- The spring reverb primitive follows the parametric spring-reverb direction: parallel spring paths, delay feedback, cascaded allpass dispersion for the chirp-like attack, damping, and small nonlinear excitation. Source notes: the AES spring waveguide overview (https://secure.aes.org/forum/pubs/conventions/?elib=13788), Julian Parker's efficient dispersion structures article record (https://aaltodoc.aalto.fi/items/7f4a9c96-47d2-4b5e-ab3d-3fc2ea69f4da), and the DAFx-11 parametric spring reverb paper (https://dafx.de/paper-archive/2011/Papers/39_e.pdf).
- The nonlinear reverb primitive follows the gated/nonlinear program direction: dense artificial reverb from parallel combs and allpass diffusers, then a keyed envelope with a deliberately abrupt close instead of a natural decay. Source notes: RingBuffer's Schroeder reverb overview (https://ringbuffer.org/dsp/Reverb/schroeder_reverb/), Csound's Schroeder/Freeverb notes on parallel combs and series allpasses (https://files.csound-tutorial.net/floss_manual/Release04/Cs_FM_04_ScrapBook/e-reverberation.html), and SourceAudio's gated reverb overview describing generous reverb followed by a gate cutoff (https://www.sourceaudio.com/blog/2022/01/14/gated-reverb/).
- The sampler primitive follows the established sampler shape of key/velocity-mapped regions, source sample-rate correction, pitch playback ratio, optional loop points, and interpolated reads. Source notes: SFZ region opcodes for `sample`, `lokey`/`hikey`, `lovel`/`hivel`, pan, and loop points (https://sfzformat.com/opcodes/), Web Audio's `AudioBufferSourceNode` notes on computed playback rate, loop start/end, and interpolated playback (https://www.w3.org/TR/webaudio-1.0/), and Physical Audio Signal Processing delay-line interpolation guidance (https://www.dsprelated.com/freebooks/pasp/Delay_Line_Signal_Interpolation.html).
- The lo-fi sampler primitive layers the sampler region model with older sampler coloration rather than claiming to exactly clone protected product identities. Source notes: the SP-1200 owner manual describes 12 significant sample bits, a fixed 26.04 kHz sample period, 12-bit linear data words, and forward-only loop handling (https://manualzz.com/doc/1729083/e-mu-systems-sp-1200-owners-manual); the MPC60 manual describes 40 kHz sampling compressed to a special 12-bit storage format (https://www.mpc-tutor.com/files/mpc-manual/MPC60_manual_v310.pdf); Web Audio's `AudioBufferSourceNode` playback section covers loop points, computed playback rate, and interpolation (https://www.w3.org/TR/webaudio-1.0/); and SFZ velocity/key region opcodes informed the zone-selection surface (https://sfzformat.com/opcodes/lovel/).
- The acid-bass primitive follows the classic bassline control set without using trademarked API names: saw/square source, cutoff, resonance, envelope modulation, decay, accent, slide, drive, and level. Source notes: Roland Cloud's TB-303 Software Bass Line manual for waveform, cutoff, resonance, env mod, decay, accent, drive, and slide-oriented controls (https://www.rolandcloud.com/CMS/getmedia/b3e2da28-1951-467e-bd79-7aae34481570/TB-303-Manual-E.pdf?ext=.pdf), and Matthew Olney's computational synthesis chapter summarizing the importance of sequencer slide/accent, oscillator, filter, fast attack-decay envelopes, and the debated ladder-filter behavior (https://olney.ai/ct-modular-book/tb-303.html).
- The drum-voice primitive follows classic analogue drum-machine building blocks without using trademarked API names: kick as a decaying sine with fast pitch transient, snare as pitched body plus snappy filtered noise, and hat as bright filtered noise plus an inharmonic square-wave bank. Source notes: Electronic Musician/MusicRadar's analogue drum synthesis guide on kick, snare, and hat structures (https://www.musicradar.com/how-to/how-to-recreate-classic-analogue-drum-sounds-in-your-daw-and-with-hardware), and Robin Whittle's TR-808 sound-modification notes describing snare noise, white-noise behavior, and six-square-wave cymbal/hat excitation (https://www.firstpr.com.au/rwi/tr-808/TR-808-Sound-Mods.pdf).
- The string-machine primitive follows classic string-ensemble building blocks: divide-down/paraphonic register sources, slow attack/release articulation, and a heavy ensemble chorus as the defining character rather than a transparent post-effect. Source notes: Vintage Synth Explorer's Solina String Ensemble summary describing fully polyphonic strings and modulation controls (https://www.vintagesynth.com/arp/solina-string-ensemble), and Arturia Solina V documentation references to the original instrument's divide-down behavior and ensemble signal flow (https://manualsnet.com/arturia/solina-v).
- The poly-synth primitive follows classic Juno-style subtractive building blocks without using trademarked API names: DCO saw/pulse, manual/LFO pulse-width motion, sub oscillator, noise, resonant VCF with envelope modulation, VCA ADSR, and chorus width. Source notes: Roland's JUNO-106 technical specifications for the DCO, sub/noise, VCF, VCA, ENV, LFO, and chorus control set (https://support.roland.com/hc/en-us/articles/201966419-Juno-106-Technical-Specifications), Roland's JUNO-106/SYSTEM-8 parameter correspondence table for PWM, saw, sub, noise, VCF, envelope, and chorus parameter grouping (https://static.roland.com/assets/media/pdf/JUNO106_SYS8_Param_corr_table_ej01_W.pdf), and the W3C/RBJ Audio EQ Cookbook for stable digital low-pass design references around the broader filter family (https://www.w3.org/TR/audio-eq-cookbook/).
- The current polyBLEP oscillator path follows the antialiasing direction from the [Valimaki/Smith oscillator literature](https://research.aalto.fi/en/publications/efficient-antialiasing-oscillator-algorithms-using-low-order-frac), while deeper oscillator variants remain future primitive work rather than pretending this pass landed them.
- The compressor is still a clean feed-forward digital design with peak envelope smoothing and soft-knee gain reduction; deeper program-dependent ballistics can build from the same core state shape later.
- Parameter smoothing, envelope following, and drift slewing use standard one-pole exponential smoothing so they are cheap, deterministic, and safe to call in real-time render loops.

## Raw-performance implications

- The largest removed cost is `JSON.stringify` plus `Array.from(Float32Array)` for sample buffers, IRs, inputs, and wavetable levels.
- The binary path still copies request bytes from JavaScript into WASM memory once per offline render, but repeated renders of the same graph now avoid rebuilding the static graph payload.
- The old full-buffer Rust render engine has been removed. Production JSON, binary, and live WASM exports all construct the typed `Runtime` path, and the former engine coverage now lives as direct runtime tests for invalid requests, modulation, block streaming, and stereo shape.
- The worklet processor source no longer embeds generated JS DSP kernels, and the live TypeScript renderer no longer keeps a native oscillator/filter/effect graph builder.
- The new runtime avoids per-block graph allocation by reusing node output buffers, and param-slot/modulation lookup no longer compares parameter strings per sample.
- The live runtime has removed the highest-frequency string dispatch, broad modulation scans, generic `NodeDef` field reads, and the second state enum match from the block render path.
- Routing renderers now hoist mono/stereo channel checks out of sample loops for pan, mono mix, and stereo composition, preserving safe slice indexing while avoiding repeated per-frame channel-shape branches in common wrapper nodes.
- Offline binary rendering now consumes the decoded graph request directly when constructing the typed runtime instead of cloning the full request. That removes an avoidable clone of sample zones, buffers, IRs, inputs, and wavetable frames before DSP starts on sample-heavy renders.
- Triggered offline binary rendering now passes trigger pitch in the compact request header, so each note can reuse the original graph object's cached static node bytes instead of cloning and recompiling the graph purely to retune source `freq` fields.
- Offline binary rendering now writes the runtime output straight into the output buffers allocated by TypeScript, removing the prior Rust-side full-render `Vec` allocation and second output copy.
- Triggered offline binary rendering now reuses one runtime instance across all triggers for a render call and adds each voice directly from WASM memory into the final TypeScript output buffers, removing per-trigger request allocation, graph decode, runtime construction, and intermediate voice arrays on the fast path.
- Fallback output mixing now adds stereo sources into mono targets with a direct averaging loop instead of allocating a temporary mono mix buffer per voice, and the stereo-target additive path hoists output bounds before entering the sample loop.
- Triggered fallback renders now convert local frame counts back to duration with a small guard offset, avoiding a floating-point round-down that could drop the final sample from per-trigger legacy renders.
- Runtime parameter access now exposes a static-scalar check, and the classic biquad, delay, and comb renderers use it to hoist unmodulated parameter reads and filter coefficient design out of their per-sample loops while keeping block-param and modulation paths sample-accurate.
- Binary graph decoding now preserves node kinds, waveform/filter/drum-voice/FM choices, parameter ids, and modulation rates as compact typed Rust values instead of allocating strings and asking runtime compilation to parse them again; JSON compatibility fields remain as the older fallback path.
- The remaining classic effect wrappers now use the same static-scalar check: `chorus`, `distortion`, and streaming `reverb` resolve stable params once per block, while block-param and graph-modulated versions still take the sample-accurate dynamic branch.
- Shared-core dynamics/color wrappers now use the same static-scalar check for `saturator`, `degrade`, and `wavefolder`, so unmodulated or scalar `AudioParam` blocks resolve their params once per render block instead of re-entering generic param/modulation lookup for every sample. Audio-rate block params and graph modulation still take the sample-accurate dynamic path.
- Shared-core echo wrappers now hoist static/scalar params for `spaceEcho`, `tapeDelay`, `microPitch`, and `multiTapDelay`, avoiding repeated generic param/modulation lookup across delay-heavy render blocks while preserving the existing sample-accurate dynamic path for modulated params.
- The remaining shared-core effect wrappers now use that same static/scalar param fast path for `ensembleChorus`, `plateReverb`, `springReverb`, `nonlinearReverb`, `tiltEq`, `stereoSpread`, `rotarySpeaker`, `compressor`, and `bitcrush`. This removes stable-parameter resolution from their per-sample loops while leaving block params and graph modulation on the dynamic sample-accurate path.
- Rust-native instrument wrappers now also hoist stable scalar slots for `sampler.instrument`, `instrument.lofiSampler`, `instrument.acidBass`, `instrument.drumVoice`, `instrument.stringMachine`, and `instrument.polySynth`, so triggered voices and live scalar-param blocks reuse one params struct per block unless graph modulation or true a-rate params require per-sample resolution.
- Foundational source, envelope, and routing wrappers now follow the same rule: constants, oscillators, wavetables, FM operators/matrices, ADSR, AR, exponential envelopes, gain, and pan all hoist scalar/static params out of their sample loops. FM keeps a small compiled static-param bundle for the six-operator hot path, while modulated and true a-rate graphs continue through the dynamic resolver.
- Public triggered WASM rendering now chooses the per-trigger binary WASM path for the small finite-tail delay shapes where repeated benchmarks show it beats reusable runtime reset: zero-feedback `delay` and no-feedback, fully-open-tone `multiTapDelay`. Larger or stateful-tail graphs keep the reusable runtime path.
- Offline stateful runtime input rendering no longer clears the full input heap on every block. Validated inputs are exact-length buffers and Rust receives the actual frame count, so each block now copies only the frames it will process.
- Triggered renders now skip provably silent post-release frames for simple gated voices (`sampler.instrument`, `instrument.lofiSampler`, `envelope.ar`, `envelope(...)`), exact wrappers (`gain`, `pan`, `mix`, `stereo`, `distortion`, `exponential`, `compressor`), dry/neutral `tiltEq`, dry `stateVariableFilter`, dry `wavefolder`, dry/stopped `rotarySpeaker`, dry-only mix wrappers, finite `stereoSpread` Haas-delay windows, finite `frequencyShifter` Hilbert-FIR tails, non-looping buffers with positive playback rate, `bitcrush` with its bounded sample-hold frames, zero-feedback `delay` with its exact delay span, classic `chorus` with its maximum modulation-delay span, `microPitch` with its bounded base-plus-sweep delay window, and no-feedback `multiTapDelay` when `tone` is fully open. This is exact, not threshold-based: unbounded or stateful-tail graphs still render the full remaining duration.
- Live worklets and package runtime helpers now prefer direct root-buffer runtime exports (`stopcock_synth_runtime_process_direct` and `stopcock_synth_runtime_process_mixed_direct`) so Rust no longer copies the rendered root node into separate WASM output buffers before JavaScript reads the runtime-owned left/right buffers. The older output-buffer ABI remains as a compatibility fallback.
- The benchmark currently shows the runtime-backed WASM paths winning across the covered public render cases. Current local ratios: simple oscillator/gain is about 1.02x faster than the JS reference on the public `render()` path, dense FM is about 4.16x faster on the binary WASM path, modulation-heavy effects about 3.14x faster on the binary WASM path, and space-echo/reverb about 2.75x faster on the public `render()` path.
- A triggered-render benchmark now compares public selected mode, reusable runtime reset, and the previous per-trigger binary render shape. Current local selected/runtime/legacy results after the frequency-shifter FIR and static-param fast paths: dense triggered effect stack selects runtime (`1461.30 ms` / `1472.89 ms` / `1483.57 ms`) because its delay/reverb tails are intentionally unbounded, sample-heavy lo-fi sampler selects runtime (`176.22 ms` / `174.31 ms` / `177.71 ms`), a gated bitcrush/compressor wrapper stack selects runtime (`67.23 ms` / `67.80 ms` / `69.81 ms`), a zero-feedback delay stack selects per-trigger binary (`18.54 ms` / `27.76 ms` / `18.59 ms`), a chorus stack selects runtime (`36.27 ms` / `36.27 ms` / `37.51 ms`), a micro-pitch stack selects runtime (`73.08 ms` / `73.10 ms` / `74.31 ms`), a stereo-spread stack selects runtime (`31.15 ms` / `31.04 ms` / `32.04 ms`), a frequency-shifter stack selects runtime (`85.62 ms` / `85.47 ms` / `87.00 ms`), a rotary-speaker stack selects runtime (`475.48 ms` / `481.65 ms` / `480.74 ms`), and a no-feedback multi-tap delay stack selects per-trigger binary (`88.13 ms` / `96.30 ms` / `87.20 ms`). Outputs match with `max diff: 0.00e+0`; delay-only and open-tone multi-tap use the consistently faster public path, and frequency shifting is back on the runtime path after removing repeated Hilbert coefficient math and static shift/mix lookup from the hot loop.
- The remaining live-runtime cost is mostly generic prior-input bounds checks, input memory copies for non-silent used WebAudio channels across the JavaScript-to-WASM boundary, the unavoidable WebAudio output copy, changed scalar-param writes, truly varying or changed a-rate param block copies, and duplicated full-graph offline/runtime render paths.

## Live AudioWorklet boundary

- Live playback now uses the WASM-backed AudioWorklet path only; there is no native WebAudio fallback graph builder left in the package source.
- The required stateful `process_block` ABI exists, and tests prove it preserves oscillator and delay state across 128-frame blocks.
- Host-driven WebAudio `AudioParam` arrays are now encoded as numeric slots in the binary runtime graph and passed to Rust on every process block. Single-value automation uses one float per param, including mixed callbacks where other params are receiving full a-rate blocks, and unchanged scalar values are cached in the generated processor so WASM memory only receives scalar writes when the value changes.
- Full-length host `AudioParam` arrays are inspected before selecting the runtime ABI. Arrays that are constant across the callback are treated as scalar for that block; varying arrays use the mixed ABI, with repeated identical blocks leaving WASM param memory untouched.
- The direct root-buffer ABI exposes stable runtime-owned left/right pointers to the generated worklet and offline runtime helpers, removing the extra Rust-side output copy in live playback and package render tests while preserving the older copied-output ABI for older embedded WASM blobs.
- Sparse authored inputs are compacted for the WASM runtime: `workletInput()` and `connectInput()` still expose original channels, while `processorOptions.wasmInputMap` maps packed WASM lanes back to host input indices during the audio callback.
- Connected but silent input buffers are detected in the generated worklet before copying into WASM. This still reads host-owned input samples, but it avoids repeated writes across the JS-to-WASM boundary for idle connected inputs and avoids stale samples when a lane goes from active to silent.

## Native plugin path

- Truce remains the intended wrapper for CLAP/VST3 plugin crates because its current docs describe `PluginLogic`, `#[derive(Params)]`, `truce::plugin!`, CLAP/VST3 defaults, and validation through `cargo truce`.
- Current local dependency check on 2026-05-22: `cargo-truce = 0.48.4` is visible through `cargo info`, but `cargo info truce`, `cargo info truce-core`, and `cargo info truce-test` still fail to resolve from crates.io in this environment. The rack processor crate therefore stays framework-agnostic for now; do not add Truce wrapper crates until `cargo truce new` can scaffold a buildable target or the Truce library dependency source is pinned.
- The framework-agnostic `stopcock_vintage_rack` and `stopcock_vintage_instruments` crates now provide the process-callable DSP cores that Truce wrappers should adapt once those dependencies are pinned.

## Next implementation target

Tighten the final raw-performance shape around the stateful Rust runtime:

1. Continue tightening the stateful runtime and remaining local helpers now that dispatch, source, routing, envelope, instrument, classic-effect, and shared-core effect rendering live in reusable modules.
2. Extend finite-tail analysis only where it can stay exact or measured tightly enough to be inaudible. The obvious no-recirculation delay cases now have exact bounds; reverb/filter/feedback/tone-smoothed threshold tails need separate measurement before they should be trimmed.
3. Investigate whether the remaining bridge loops can be measured against real browser profiles, especially host-owned input reads, JavaScript reads from runtime-owned output buffers, and truly varying a-rate automation.
4. Wrap `stopcock_vintage_rack` and `stopcock_vintage_instruments` with Truce once dependencies are pinned, keeping MIDI/event translation and preset state outside the audio hot path.
5. Keep the JSON ABI as a compatibility fallback only; all normal package entrypoints should continue preferring the binary/runtime route.
