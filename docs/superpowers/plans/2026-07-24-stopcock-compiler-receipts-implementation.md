# Stopcock compiler receipts and `stopcock check` implementation plan

> **Status:** proposed near-term product workstream.
>
> **Canonical parent:** compiler fallback, tier topology, production/debug
> isolation, and performance gates remain owned by
> [`2026-07-24-stopcock-v2-performance-density-superplan.md`](./2026-07-24-stopcock-v2-performance-density-superplan.md).
> This plan expands its S7, S9, S10, and release-evidence requirements.
>
> **Dependency:** stable semantic IDs and hashes come from
> [`2026-07-24-stopcock-semantic-operator-protocol-implementation.md`](./2026-07-24-stopcock-semantic-operator-protocol-implementation.md).

## Outcome

Ship a versioned machine-readable receipt format and a human-readable
`stopcock check` command that make specialization inspectable without
overstating what the compiler knows.

For every discovered pipeline site, the build receipt answers:

- what source site and import surface were recognized;
- which semantic operations and boundaries were planned;
- whether transformation occurred;
- which static execution strategy was emitted or retained as fallback;
- why a transformation, tier, or backend was rejected;
- which compiler-owned allocations are statically expected;
- which semantic mode applies;
- which release evidence supports the compiler/lowering version.

Optional runtime profiles answer a different set of questions:

- which runner actually executed;
- observed input and consumed-item counts;
- observed segment selection, hotness, and timings;
- observed compiler-owned allocation counters where instrumentation exists.

Release evidence answers a third set:

- which independent fixtures, differential suites, law suites, benchmark
  corpus, runtimes, and packed artifacts passed for the shipped version.

These records are linked but never collapsed into one ambiguous “verified”
badge.

## Existing foundations

- `packages/fp/src/compile.ts` already returns static pipeline explanations and
  limited runner statistics.
- `packages/fp-compiler/src/types.ts` already models transformed/skipped sites.
- the compiler plugin already supports summary/verbose/error diagnostics;
- source maps already exist for transformed output;
- Plan/interpreter/compiler differential suites already test callback traces
  and results;
- benchmark reports already carry source, compiler, supported-operation, and
  corpus hashes;
- the 2.0 plan already requires production/debug separation and truthful tier
  selection.

The work is primarily a schema, identity, aggregation, and honesty problem—not
permission to make static diagnostics claim runtime facts.

## Evidence classes

### 1. Build receipt

A deterministic compiler-owned record emitted without executing user code:

```ts
export interface BuildReceipt {
  readonly kind: "stopcock.build-receipt"
  readonly schemaVersion: 1
  readonly id: string
  readonly producer: ProducerIdentity
  readonly source: SourceIdentity
  readonly site: SourceSite
  readonly imports: readonly ImportIdentity[]
  readonly semanticMode: "exact" | "pure"
  readonly plan?: StaticPlanReceipt
  readonly disposition: SiteDisposition
  readonly allocationEstimate?: AllocationEstimate
  readonly evidenceRefs: readonly EvidenceReference[]
}
```

It may report:

- recognized semantic IDs, names, domains, cardinality, and bindings;
- planned segments and materialization/domain boundaries;
- emitted AOT lowering and retained fallback imports;
- static capability misses;
- compiler-owned result/temporary allocation estimates;
- generated code/source-map identities;
- exact or pure mode.

It may not report observed item counts, observed early exit, wall time, runtime
executor selection, callback allocations, engine allocations, or “this exact
user pipeline passed semantic tests.”

### 2. Runtime profile

An explicitly enabled development record linked to one build receipt:

```ts
export interface RuntimeProfile {
  readonly kind: "stopcock.runtime-profile"
  readonly schemaVersion: 1
  readonly buildReceiptId?: string
  readonly planHash: string
  readonly runtime: RuntimeIdentity
  readonly executions: number
  readonly observed: ObservedExecution
  readonly privacy: RuntimeProfilePrivacy
}
```

It may report:

- actual selected executor/tier;
- actual segment runners;
- input and consumed-item counts;
- size/selectivity/hotness buckets;
- compiler-owned instrumented allocation counters;
- queue/transfer/compile/execute timings for participating backends;
- fallback or deoptimization events.

Instrumentation is opt-in, development-only by default, and separately
benchmarked. A profile generated by instrumented code is never used as an
unqualified production throughput result.

### 3. Release evidence

A signed-or-hashed repository/CI artifact:

```ts
export interface ReleaseEvidence {
  readonly kind: "stopcock.release-evidence"
  readonly schemaVersion: 1
  readonly release: string
  readonly semanticProtocolHash: string
  readonly compilerHash: string
  readonly generatedOutputHash: string
  readonly packedArtifactHashes: readonly string[]
  readonly corpus: readonly CorpusEvidence[]
  readonly runtimeMatrix: readonly RuntimeEvidence[]
  readonly status: "qualified" | "failed" | "partial"
}
```

It states what the shipped implementation passed on named artifacts and
runtimes. A build receipt may say “covered by release evidence X”; it must not
rewrite that as “semantic equivalence proved for this application.”

## Identity and reproducibility

All receipt IDs are hashes of canonical data, not timestamps or absolute
machine paths.

Required identities:

- normalized repo-relative source path;
- source content hash;
- line/column and stable site fingerprint;
- import source and exported symbol;
- semantic protocol version/hash;
- plan semantic IDs and plan hash;
- compiler package/version/source hash;
- compiler configuration hash;
- generated code and source-map hash;
- fallback/tier identity;
- tool/host adapter version;
- linked evidence IDs.

Rules:

- absolute user home paths are stripped from portable receipts;
- path normalization never merges two distinct source files;
- timestamps, durations, and machine identity belong only to observed profiles
  and evidence runs;
- deterministic builds produce byte-identical build-receipt JSON;
- unknown schema versions fail explicitly;
- receipts use JSON-safe finite values and stable key ordering;
- optional signing comes after deterministic hashing and is not required for
  local use.

## Static plan and disposition model

Every discovered site has exactly one disposition:

```ts
type SiteDisposition =
  | { readonly kind: "transformed"; readonly lowering: LoweringIdentity }
  | { readonly kind: "fallback"; readonly executor: ExecutorIdentity; readonly reason: Reason }
  | { readonly kind: "skipped"; readonly reason: Reason }
  | { readonly kind: "error"; readonly reason: Reason }
```

Reasons use stable codes plus human detail:

- unsupported operator;
- opaque callback;
- mutable or unsafe capture;
- unsupported binding form;
- exact/pure semantic mismatch;
- materialization or domain boundary;
- unsupported import/facade;
- stale semantic/lowering hash;
- unavailable backend;
- CSP or host restriction;
- strict-scope exclusion;
- compiler implementation defect.

Human text can improve without breaking consumers; codes are versioned.

### Allocation estimates

Static receipts distinguish:

- `compiler-owned-result`;
- `compiler-owned-intermediate`;
- `compiler-owned-metadata`;
- `unknown-callback`;
- `unknown-engine`;
- `external-backend`.

Each estimate carries:

```ts
interface AllocationEstimate {
  readonly classification: "exact-static" | "upper-bound" | "shape-dependent" | "unknown"
  readonly compilerOwnedResults?: number
  readonly compilerOwnedIntermediates?: number
  readonly explanation: string
}
```

Never summarize unknown callback/engine allocations as “one allocation.”

## Runtime profile privacy

Default runtime profiles contain no values, callback source, headers, URLs,
row contents, image bytes, or stack-local user objects.

Allowed default observations:

- logarithmic input-size bucket;
- selectivity bucket;
- consumed count or bucket;
- execution count/hotness;
- operation/segment IDs;
- timings and compiler-owned counters.

Exact sizes require explicit configuration. Stack traces and source snippets
remain in local developer output unless a caller deliberately writes them to a
file. The profile API accepts a redaction hook and records which privacy mode
was used.

## CLI and integration surface

Add a binary owned by `@stopcock/fp-compiler`:

```text
stopcock check [paths]
  --format pretty|json|jsonl
  --receipt-dir <dir>
  --strict
  --require-transform <glob>
  --evidence <manifest>
  --verify-evidence
  --profile <profile-file>
```

Behavior:

- default `check` reads build receipts and prints a summary;
- it does not run application code, tests, or benchmarks implicitly;
- `--strict` fails only on configured included scopes and stable reason policy;
- `--require-transform` fails when a matching site was not transformed;
- `--verify-evidence` verifies hashes and status of a supplied evidence
  manifest; it does not rerun the evidence corpus;
- a separate documented command/job produces release evidence;
- a separate explicit development harness produces runtime profiles;
- missing optional profiles never fail an ordinary build.

The compiler plugin can emit receipts directly or through a host-neutral
collector. Vite, Rollup, Rolldown, esbuild, Webpack, and Rspack adapters must
produce the same schema and semantic content.

## Human report

The pretty renderer groups by source site:

```text
src/orders.ts:42  exact  transformed

  map -> filter -> take
  emitted       AOT fused loop
  fallback      compact fusion
  boundaries    none
  allocations   1 compiler-owned result; callback/engine allocations unknown
  evidence      fp-2.0.0-next.N / corpus abc123

  profile       3 executions; 14 inputs consumed on latest instrumented run
                runtime profile, not a build-time guarantee
```

Use distinct visual labels for:

- static;
- observed;
- release evidence;
- estimate;
- unknown.

Do not display a single green checkmark that erases those distinctions.

## Implementation slices

### Slice 0 — Freeze schema vocabulary and claims policy

1. Inventory every existing explanation, diagnostic, benchmark identity, and
   compiler fallback reason.
2. Define stable reason codes and evidence-class terminology.
3. Write examples of permitted and forbidden claims.
4. Freeze version-one JSON fixtures before implementation.

**Gate:** reviewers can identify the evidence class of every field without
reading prose.

### Slice 1 — Emit deterministic build receipts

1. Add schema types and canonical JSON serialization.
2. Extend compiler diagnostics with semantic IDs, plan segments, import/fallback
   tier, source hash, generated output hash, and stable reasons.
3. Emit per-site JSON/JSONL from every supported build host.
4. Preserve fail-open compiler behavior by default.

**Gate:** equivalent builds across supported hosts produce semantically
equivalent receipts and repeated builds are byte-identical after normalized
host metadata.

### Slice 2 — Integrate semantic protocol and tier diagnostics

1. Source operation names/contracts from the canonical semantic protocol.
2. Link lowerings to semantic/evidence hashes.
3. Report the actual static fallback implied by each import facade.
4. Reject stale lowering hashes and report the fallback.

**Gate:** runtime explain, compiler output, and receipts use the same semantic
and lowering identities.

### Slice 3 — Build release-evidence manifests

1. Extend existing differential/performance report generators to emit one
   versioned evidence envelope.
2. Preserve raw samples and independent correctness results.
3. Include source, generated, dist, tarball, fixture, runtime, OS, architecture,
   and case-manifest identities.
4. Add hash verification and partial/failed status handling.

**Gate:** no successful receipt references absent, stale, failed, or mismatched
release evidence.

### Slice 4 — Add opt-in runtime profiling

1. Add development-only counters outside hot inner loops where possible.
2. Instrument consumed input, selected runners, fallbacks, and
   compiler-controlled allocations.
3. Measure instrumentation overhead by plan family.
4. Add privacy modes, redaction, reset, and bounded aggregation.

**Gate:** profiling is absent from production closures by default, bounded when
enabled, and its overhead is reported.

### Slice 5 — Ship `stopcock check`

1. Implement pretty, JSON, and JSONL renderers.
2. Add scoped strict policies and evidence verification.
3. Merge build receipts with explicitly supplied profiles by stable IDs.
4. Provide actionable rejected-transformation guidance.
5. Test exit codes and CI annotations.

**Gate:** a clean packed consumer can run `stopcock check` without workspace
source access or application execution.

### Slice 6 — Documentation and product proof

1. Document static versus observed versus release evidence.
2. Add recipes for local builds, CI strict scopes, runtime profiling, and
   evidence verification.
3. Publish representative transformed, fallback, boundary, and unsupported
   reports.
4. Use the worker-image and incremental prototypes as later multi-backend
   receipt examples only when they exist.

## Test matrix

- transformed, partially transformed, skipped, fallback, and compiler-error
  sites;
- exact and pure modes;
- root, compact, optimized, compatibility, alias, namespace, and mixed imports;
- opaque, closure-capturing, bound/member, destructured, throwing, and unsafe
  callbacks;
- Option/Result terminals and identity-sensitive results;
- source maps through every packed build host;
- deterministic ID/path/hash generation;
- absolute path and user-data redaction;
- unknown/new schema version behavior;
- missing, stale, failed, and partial release evidence;
- profile merge with missing or mismatched receipt IDs;
- profiling disabled/enabled bundle and throughput comparison;
- pretty, JSON, JSONL, CI exit codes, and malformed receipt input.

## Acceptance criteria

- Every discovered compiler site receives one deterministic disposition.
- Build receipts contain no observed-runtime claims.
- Runtime profiles are opt-in and clearly labelled observed.
- Release evidence refers to exact corpora and artifacts rather than generic
  “tests passed” prose.
- Static allocation output identifies ownership and uncertainty.
- Unsupported transformations retain correct synchronous fallback.
- Production root/direct/compact closures retain their size and debug-isolation
  gates.
- Packed consumers can produce and inspect receipts across supported build
  hosts.
- The public product claim is “Stopcock specializes typed TypeScript
  pipelines—and shows its work,” not universal verification.

## Rollback

Receipt emission, profiling, evidence generation, and CLI rendering are
separate switches. Disabling receipts must not alter transformed code.
Disabling profiling must remove its production cost. If a host adapter cannot
emit a truthful field, omit/mark it unknown rather than synthesizing a value.
Never recover from schedule pressure by merging static, observed, and release
evidence into one unqualified status.
